# 25일차 — 회원 데이터와 기존 게스트 연결 설계

2026-10-18 구현. **25일차의 회원 데이터 기반·마이그레이션·전환 설계 완료** 기록입니다. 회원가입·로그인 API와 화면은 26일차, 작업실 권한·초대·실시간 세션 연계는 27일차 작업입니다. 현재 화면은 기존 게스트 방식으로 동작합니다.

## 구현한 데이터 모델

| 테이블 | 컬럼 | 제약과 용도 |
|---|---|---|
| `users` | `user_id`, `login_id`, `display_name`, `password_hash`, `created_at`, `updated_at` | 로그인 ID UNIQUE, `utf8mb4_unicode_ci` 비교로 대소문자만 다른 ID 중복 거부. 표시 이름 중복 허용. 비밀번호 해시용 255자 컬럼 |
| `user_sessions` | `session_id`, `user_id`, `token_hash`, `expires_at`, `revoked_at`, `created_at` | SHA-256 토큰 해시 UNIQUE, 회원 외래키, 회원·만료 복합 인덱스. 원문 토큰 저장 금지 |
| `guest_user_links` | `guest_id`, `user_id`, `linked_at` | `guest_id` 기본키로 게스트당 회원 한 명. 회원 한 명에 여러 게스트 연결 가능. 두 ID 모두 외래키 |

`user_id`와 `guest_id`는 서로 다른 식별자입니다. 같은 숫자나 같은 표시 이름이라는 이유로 같은 사람으로 취급하지 않습니다. 기존 작업실 작성자·멤버십·업무 담당자·파일 업로더·접속 티켓은 계속 `guest_id`를 참조합니다. 회원의 작업실 권한은 향후 검증된 연결을 통해 해당 게스트의 멤버십을 조회하는 방식으로 확장합니다.

회원 세션은 `guest_sessions`와 별개입니다. 향후 인증에서는 만료되지 않았고 `revoked_at IS NULL`인 회원 세션만 인정하며, 회원 인증과 작업실 역할 검사를 각각 수행해야 합니다. 현재는 테이블만 추가했으며 인증 API와 쿠키 발급은 미구현입니다.

## 기존 게스트의 전환 시나리오

| 상황 | 확정한 처리 규칙 | API 구현 단계 |
|---|---|---|
| 신규 회원 | 회원 생성·로그인 후 새로운 게스트 ID를 만들어 연결. 동명이인 자동 연결 금지 | 26~27일차 |
| 기존 게스트 연결 | 회원 비밀번호 재확인과 유효한 현재 게스트 세션을 함께 검증. 서버가 세션에서 게스트 ID를 결정하고 트랜잭션 안에서 연결 | 27일차 |
| 이미 같은 회원에 연결 | 기존 연결 확인 후 중복 생성 없이 처리 | 27일차 |
| 다른 회원에 연결 | 연결 거부. 초대 코드·표시 이름·요청 본문의 ID로 덮어쓰기 금지 | 27일차 |
| 여러 작업실의 게스트 | 각 게스트 세션의 소유를 확인한 경우에만 같은 회원에 연결. 이름으로 일괄 병합 금지 | 27일차 |
| 유효한 게스트 세션 없음 | 자동 이전 거부. 초대 코드만으로 기존 게스트 소유 확인 금지 | 27일차 |
| 게스트 방식 유지 | 기존 기능 유지. 마이그레이션은 회원·세션·연결 행을 자동 생성하지 않음 | 25일차 보존 검증 완료 |

**연결 활성화 전 필수 보호:** 현재 `GuestController::join()`은 이름과 초대 코드로 기존 게스트를 재사용할 수 있습니다. 회원 연결 API를 추가할 때 연결된 게스트를 이 경로로 재사용하지 못하도록 함께 차단해야 합니다. 연결 시 기존 게스트 세션과 미사용 접속 티켓을 폐기·재발급하고 이미 연결된 Socket.IO 세션도 정리하여 이전 세션의 권한 잔존을 차단합니다. 이 보호를 구현·검증하기 전에는 연결 기능을 노출하지 않습니다.

유효한 게스트 세션의 보유는 현재 접근 권한의 증거이며 실명이나 과거 실제 작성자의 신원을 보증하지 않습니다. 세션을 잃은 사용자를 표시 이름만으로 복구하는 기능은 제공하지 않습니다.

## 삭제와 참조 정책

- 연결이 남아 있는 회원 삭제는 외래키 `RESTRICT`로 거부합니다. 계정 삭제 API를 추가할 때 연결·권한·기존 세션의 처리를 먼저 확정해야 합니다.
- 연결이 없는 회원을 삭제하면 그 회원의 `user_sessions`만 연쇄 삭제합니다. 기존 게스트·작업실·업무는 회원 삭제로 지우지 않습니다.
- 게스트가 삭제되면 그 게스트의 연결 행만 연쇄 삭제합니다. 회원과 다른 게스트의 연결은 보존합니다.
- 연결 해제나 다른 회원으로의 변경 API는 이번 단계에 없습니다. 외래키는 소유 확인을 대신하지 않으며 실제 연결은 서버 인증·권한 검사 후에만 수행해야 합니다.
- **시연 전체 초기화는 별도 정책입니다.** 기존 `reset-demo.php`의 전체 데이터 초기화 대상에 회원·회원 세션·게스트 연결도 포함했습니다. 외래키 검사를 끈 `TRUNCATE`에서는 연쇄 삭제가 동작하지 않으므로 연결 행을 명시적으로 지워 게스트 번호 재사용 시 이전 회원과 결합되지 않게 합니다. `--dry-run`은 회원별 테이블의 삭제 대상 수도 표시합니다. 실제 초기화는 계정까지 삭제하므로 운영 DB에서 실행하지 않습니다.

## 신규 설치와 기존 DB 보정

신규 설치는 `database/schema.sql`, 기존 설치는 `apps/php-api/bin/migrate.php`를 사용합니다. `Schema.php`에 세 테이블을 등록하여 시작 스크립트와 사전 점검이 기존 경로로 누락을 감지합니다. 기존 테이블을 재생성하거나 행을 수정하는 SQL은 추가하지 않았습니다. DDL은 자동 커밋될 수 있으므로 적용 전 백업이 필요합니다. 중간 실패 원인을 해결하고 재실행하면 이미 생성된 테이블을 건너뜁니다.

```powershell
& 'C:\xampp\php\php.exe' apps/php-api/bin/migrate.php # 기존 DB의 누락 테이블 추가
& 'C:\xampp\php\php.exe' apps/php-api/tests/member-schema.php # 임시 DB 기반 검증
```

테스트는 `.env`의 서버 접속 정보로 임의의 `taskcanvas_d25_` DB를 새로 생성하므로 DB 생성·삭제 권한이 있는 개발용 계정이 필요합니다. 운영 DB를 선택하는 SQL을 제외하고 임시 DB에만 신규 스키마·가상 데이터를 적용하며 실행 후 자기가 만든 DB만 삭제합니다. 운영 회원이나 실제 비밀번호를 사용하지 않습니다.
