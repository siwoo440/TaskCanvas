# 29일차 분석 대시보드 상세 설계

작성일: 2026-10-18 · 단계: 방향 승인 후 상세 설계 검토

---
## 1. 목적과 완료 조건

작업실의 실제 저장 업무를 KPI·차트·표로 확인하는 분석 화면을 추가한다. 사용자가 승인한 범위는 별도 분석 화면, KPI 4개, 상태 도넛, 담당자 막대, 일별 생성 추이, 20개 단위 업무 표, 공통 필터, 로컬 차트 파일, 수동 갱신과 인증·화면 상태 처리다.

완료 조건은 다음과 같다.

- 작업실에서 분석 화면에 진입하고 다시 작업실로 돌아갈 수 있다.
- 같은 생성일·상태·담당자 조건이 카드·차트·표 전체에 적용된다.
- 업무가 여러 보드에 표시되어도 업무 원본 한 건으로 집계된다.
- 인증되지 않은 사용자와 다른 작업실의 사용자는 조회할 수 없다.
- 작업실 전환·로그아웃 후 이전 데이터와 늦게 도착한 응답이 표시되지 않는다.
- 빈 데이터·통신 오류·모바일 화면에서도 조작과 의미 파악이 가능하다.

## 2. 기존 코드와 접근 방식

28일차 `TaskAnalytics`와 `AnalyticsController`가 제공하는 summary API를 기반으로 한다. 현재 화면은 `index.html`의 home·board 뷰와 `app.js`의 작업실·인증 상태 관리로 구성되어 있다.

| 접근 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 전용 dashboard API와 같은 문서 안의 분석 뷰 | 응답 하나로 필터·스냅샷 일치, 기존 인증·작업실 상태 재사용 | API 추가와 조회 코드 분리가 필요하며 채택 |
| summary와 업무 목록을 각각 호출 | 기존 API 재사용 범위가 큼 | 서로 다른 시점의 카드·표와 필터 중복 처리 발생 |
| 별도 HTML 문서에서 분석 화면 구성 | 화면 파일의 독립성 | 인증·작업실 선택·전환 상태를 별도 복구해야 함 |

새 `view-analytics` 섹션을 추가하되 조회·렌더링·차트 수명 관리는 전용 JS 모듈에 둔다. `app.js`는 진입·복귀·인증 변경 연결을 담당한다. 데이터 저장 구조 변경과 DB 마이그레이션은 없다.

## 3. 화면과 사용자 흐름

작업실 상단에 ‘분석 대시보드’ 버튼을 배치한다. 작업실을 선택한 열람자·편집자·관리자 모두 사용할 수 있다. 독립 게스트와 회원 연결 게스트 모두 기존 권한 규칙을 따른다.

분석 화면 순서는 다음과 같다.

1. 작업실 이름, ‘작업실로 돌아가기’, ‘새로고침’ 버튼
2. 생성 시작일·종료일, 상태, 담당자, ‘조회’ 버튼
3. 적용된 기간·조건과 마지막 성공 조회 시각
4. KPI 4개
5. 상태 도넛과 담당자별 전체·완료 막대 차트
6. 일별 업무 생성 수 선 그래프
7. 업무 표와 이전·다음 페이지 버튼, 현재 페이지·전체 건수

| KPI | 값 | 보조 설명 |
| --- | --- | --- |
| 전체 업무 | tasks.total | 선택 조건에 해당하는 업무 수 |
| 업무 완료율 | tasks.completion_rate | 완료 수 / 전체 업무 수 |
| 마감 초과 | due.overdue | 서울 기준 오늘 이전 마감의 미완료 업무 |
| 체크리스트 완료율 | checklist.completion_rate | 완료 항목 수 / 전체 항목 수 |

완료율은 소수 첫째 자리까지 표시하며 분모가 0이면 0%다. 보조 설명에 완료/전체 건수를 함께 표시한다. 마감 초과 KPI도 생성일·상태·담당자 조건의 영향을 받는다.

처음 진입하면 최근 30일을 조회한다. 화면을 닫으면 필터와 결과를 폐기하며 다음 진입은 기본 조건으로 시작한다. 화면 안에서는 조회·새로고침·페이지 이동에 적용된 조건을 유지한다. 필터를 수정한 뒤 조회하지 않은 상태와 실제 적용 조건을 구분한다. 페이지 이동과 새로고침은 마지막으로 적용한 조건을 사용한다.

## 4. 조회 API와 필터 계약

추가 경로: `GET /api/projects/{id}/analytics/dashboard`

기존 `/analytics/summary`의 응답·필터·날짜 생략 의미는 유지한다. 공통 필터 검증과 SQL 조건 생성을 분리하여 두 API가 재사용한다. dashboard에만 기간 기본값·최대 범위와 페이지 규칙을 적용한다.

| 쿼리 | 규칙 |
| --- | --- |
| created_from, created_to | 실제 존재하는 1000~9999년 YYYY-MM-DD, 양끝 날짜 포함 |
| 두 날짜 모두 생략 | 서울 기준 오늘-29일 ~ 오늘 |
| created_from만 입력 | 종료일은 서울 기준 오늘 |
| created_to만 입력 | 시작일은 종료일-29일 |
| 기간 길이 | 양끝 포함 1~366일, 역순·초과·기본값 계산 후 DB 날짜 범위 이탈은 400 |
| status | 생략 시 전체, todo·doing·done만 허용 |
| assignee_id | 생략 시 전체, 정규 양의 정수 또는 unassigned |
| page | 생략 시 1, PHP 정수 범위의 정규 양의 정수 |

빈 문자열·배열·알 수 없는 키·유효하지 않은 값은 400으로 거부한다. UI의 ‘전체’는 해당 쿼리를 생략한다. 담당자 ID의 문법이 유효하지만 해당 작업실에 업무가 없으면 빈 결과를 반환한다. 다른 작업실의 담당자 정보는 반환하지 않는다.

고정 page_size는 20이다. 정렬은 `created_at DESC, task_id DESC`이며 동일 생성 시각에도 안정적인 순서를 보장한다. 범위를 벗어난 페이지는 마지막 페이지로 보정하고 실제 적용 페이지를 응답한다. 0건일 때 page=1, total_pages=1, rows=[]다.

## 5. 응답 구조

JSON 응답은 다음 필드 계약을 갖는다. 아래 표는 구조 명세이며 실제 데이터를 대신하는 예시 수치를 만들지 않는다.

| 필드 | 내용 |
| --- | --- |
| project_id, time_zone, as_of_date | 작업실 ID, Asia/Seoul, 마감 분류 기준일 |
| filters | 기본값까지 적용한 created_from·created_to·status·assignee_id |
| summary | 기존 summary의 tasks·assignees·due·checklist와 같은 구조·계산식 |
| daily_created | 날짜 오름차순의 date·count 목록, 적용 기간의 모든 날짜 포함 |
| assignee_options | assignee_id·display_name 목록, 작업실 안에서 ID 중복 제거 |
| pagination | page·page_size·total·total_pages |
| rows | 현재 페이지 업무 목록 |

rows의 각 업무는 task_id·title·status·assignee_id·assignee_name·due_at·created_at·checklist를 제공한다. checklist는 total·done·completion_rate다. 업무 설명과 체크리스트 개별 제목은 조회하지 않는다. task_id와 assignee_id는 정수이며 미배정 ID·이름과 마감일은 null을 허용한다. 프런트엔드는 미배정을 ‘미배정’, 미지정 마감을 ‘없음’으로 표시한다. 날짜 시각 문자열은 기존 DB의 서울 현지 시각 의미를 유지한다.

담당자 선택지는 현재 작업실 멤버와 그 작업실 업무에 실제 지정된 담당자를 합친 목록이다. 필터와 페이지에 따라 선택지가 사라지지 않게 전체 작업실 범위에서 조회한다. 이름이 같아도 ID가 다르면 별도 선택지와 막대로 표시하고 UI에 ID를 보조 표기한다. ‘전체’·‘미배정’ 선택지는 UI에서 추가한다.

## 6. SQL 집계와 데이터 일관성

tasks를 집계 기준으로 삼고 board_objects와 조인하지 않는다. 체크리스트는 업무별 사전 집계 후 연결하여 업무 수가 항목 수만큼 늘어나지 않게 한다. 담당자 집계도 이름 대신 ID를 기준으로 한다.

dashboard의 요약·일별 생성 수·표·담당자 선택지는 같은 PDO 연결에서 명시적으로 REPEATABLE READ 읽기 전용 트랜잭션의 일관된 스냅샷으로 조회한다. 첫 집계 이후 다른 요청이 업무를 생성·수정·삭제해도 해당 응답 안의 전체 건수와 페이지 데이터는 같은 시점을 따른다. 성공 시 종료하고 예외 시 롤백하여 트랜잭션을 남기지 않는다. 인증·역할 검증은 조회 시작 전에 기존 방식으로 수행하며 이후 각 요청에서도 다시 수행한다.

요청 시작 시 서울의 오늘 날짜를 한 번만 계산해 모든 마감 경계와 기본 기간에 재사용한다. summary를 재사용할 때도 이 기준일을 전달하여 자정을 사이에 둔 응답 내부 불일치를 방지한다. 날짜 필터는 created_at에 직접 경계 비교를 사용한다. 일별 집계에서만 날짜 그룹을 만들고 비어 있는 날짜는 PHP에서 0으로 채운다. 일별 생성 수 합계와 summary.tasks.total, pagination.total이 일치해야 한다.

완료율·마감 분류·알 수 없는 기존 상태의 other 집계는 28일차 규칙을 유지한다. 선 그래프는 ‘일별 업무 생성 수’로 명시하며 과거 시점의 완료율이나 완료 이력으로 해석하지 않는다.

## 7. 차트와 접근성

Chart.js의 고정 버전 UMD 파일과 라이선스를 저장소의 공개 정적 파일 경로 `apps/frontend/public/lib/chartjs/`에 포함한다. 구현 단계에서 공식 배포물·버전·라이선스를 확인하고 출처와 버전을 기록한다. 실행 시 CDN에 접속하지 않는다. 직접 작성한 코드에는 Allman 스타일과 줄별 짧은 한글 명사형 주석을 적용한다. 외부 라이브러리 원본과 라이선스는 보존한다.

- 도넛: todo·doing·done·other 상태 수, 한글 범례·건수 제공
- 막대: 담당자별 전체·완료 업무 수, ID로 구별, 담당자가 많으면 내부 스크롤로 모두 표시
- 선: 적용 기간의 일별 생성 수, 0건 날짜 포함, 정수 눈금과 과도한 날짜 라벨 생략
- 차트별 텍스트 요약 또는 접근 가능한 데이터 표 제공, 색상만으로 구분하지 않음
- 표 제목·열 제목·입력 label·포커스 표시·상태 안내 제공

차트의 숫자는 API 응답만 사용한다. 0건은 안내문과 0 KPI로 표시하고 임의의 차트 조각을 만들지 않는다. 360px 너비에서는 카드와 차트를 세로 배치하고 넓은 표의 가로 스크롤을 표 영역 안으로 제한한다.

## 8. 요청·인증·오류 수명 관리

분석 모듈은 열기·조회·닫기 역할을 갖는다. 화면 열기, 조회 조건 변경, 페이지 이동, 닫기마다 요청 세대 번호를 갱신한다. 응답의 세대·작업실·활성 화면이 현재 상태와 일치할 때만 렌더링한다. 이전 요청의 성공·실패 모두 현재 화면 상태를 바꾸지 못한다.

새 요청 시 기존 결과와 차트를 비우고 로딩을 표시하여 이전 조건의 숫자를 새 조건으로 오인하지 않게 한다. 중복 조작을 제한하고 로딩 종료도 현재 요청만 수행한다. 성공 시 실제 적용 조건과 페이지를 서버 응답으로 확정한다.

| 상황 | 처리 |
| --- | --- |
| 401 | 결과 폐기, 기존 인증 만료 흐름 실행 |
| 403 또는 작업실 소멸 | 결과 폐기, 작업실 접근 해제 및 기존 화면 복귀 흐름 실행 |
| 400 | 조건 오류 안내와 입력 수정 가능 상태, 이전 결과 재표시 금지 |
| 네트워크·서버 오류 | 오류 안내, 동일 적용 조건으로 재시도 가능 |
| 차트 파일 로드 실패 | 오류 안내와 KPI·접근 가능한 표 유지 |
| 회원 변경·로그아웃·작업실 선택 변경·화면 닫기 | 요청 무효화, 결과 초기화, Chart 인스턴스 파기 |

분석 화면에서도 기존 작업실 실시간 연결의 인증 만료·작업실 삭제 통지를 유지한다. 실시간 업무 이벤트로 매번 자동 조회하지 않으며 수동 새로고침으로 반영한다. 기존 포커스 복귀 시 회원·게스트 재검증 흐름이 대시보드 폐기에도 적용되게 연결한다.

## 9. 변경 범위와 검증

예상 변경은 TaskAnalytics의 공통 조회 분리, dashboard 서비스·컨트롤러 경로, index.html의 진입 버튼과 분석 뷰, 전용 JS·CSS, 로컬 차트 파일·라이선스, API 문서와 테스트다. 인증·권한 모델 자체는 변경하지 않는다.

| 검증 | 확인 항목 |
| --- | --- |
| 분리 MariaDB·PHP API | 기본 30일, 단일 날짜 기본값, 윤일·역순·366일 경계·잘못된 키와 페이지 |
| 집계 정합성 | 보드 중복 참조, 체크리스트 다건, 동명 담당자, 미배정, 기존 other 상태, 0건 |
| 페이지 | 20·21건 경계, 동일 생성 시각 정렬, 마지막 페이지 보정, 필터 변경 후 1페이지 |
| 스냅샷 | 조회 중 별도 DB 연결에서 업무 변경, 같은 응답의 요약·추이·표 수치 일치 |
| 보안 | 비로그인·다른 작업실·열람자·회원 쿠키 누락·로그아웃 후 접근 |
| JS 동작 | 응답 역전, 이전 오류 무시, 화면 닫기와 계정·작업실 변경 후 결과 폐기 |
| 실제 브라우저 | 진입·복귀, 카드·차트·표, 조회·페이지·새로고침, 빈 결과·오류, 360px·키보드 조작 |

## 10. 범위 경계와 Git 처리

기간·상태·담당자 조건은 이번 화면의 숫자를 맞추기 위한 기본 조회다. 저장 뷰, 자동 주기 갱신, CSV 내보내기, 차트 선택으로 업무 이동, 업무 변경 이력, 외부 데이터 가져오기는 각각 예정된 후속 일정에 둔다.

상세 설계 승인 후 구현 계획을 작성하고 계획 검토·실행 방식 선택을 거친다. 기존 사용자 지시에 따라 main에서 작업하며 별도 브랜치를 만들지 않는다. 설계와 계획은 검토 이력으로 로컬 커밋하고 구현·검증 완료 후 29일차 최종 커밋에 통합하여 main에 푸시한다. 기존 26~28일차 커밋은 유지한다.
