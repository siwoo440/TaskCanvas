# 4인 역할 WBS 및 3주 일정

> **2026-10-20 최신 일정(우선 적용): [30~78일차 재배치표](30-roadmap-reordered.md).** 1~29일차 구현 완료 기록은 유지한다. 30~68일차 내부 기능·안전장치 → 69~73일차 외부 API·서비스 연동 → 74~78일차 종합 테스트·학교 LAN·제출 검증 순으로 재편했다. 아래 원래 3주 계획과 이전 일정 설명은 역사적 기록으로 읽되, 서로 다른 개발 일차가 나오면 재배치표를 우선한다. 각 구현 중 기본 단위·무결성 검사는 필수이며 최종 종합 테스트만 뒤로 모은다.

## 이후 단계 계획 — DB 회원인증·데이터 기반 대시보드·공공데이터 불러오기

> **계획 상태 (2026-10-15):** 1~24일차의 기존 기능과 구현 기록을 보존합니다. 아래 25일차 이후 항목은 **신규 개발 계획이며 아직 구현 완료가 아닙니다.** 이번 과제 추가 조건은 **DB 기반 사용자 등록·로그인, DB에 저장된 데이터 활용, 통계·차트가 있는 자체 설계 대시보드**입니다. 공공데이터는 데이터를 쉽게 가져오는 확장 기능으로 포함합니다. 기존 시연 범위와 새로운 과제 범위를 혼동하지 않습니다.

**2026-10-20 구현 상태 갱신:** GitHub `main`의 1~29일차 구현 기록을 확인했다. 27일차 회원 권한·실시간 세션, 28일차 SQL 통계, **29일차 KPI·차트·업무 표 대시보드까지 구현 기록이 있다.** 30일차 업로드·원본 미리보기를 추가 구현·검증했다([결과](30-file-preview.md)). 31일차 컬럼 매핑·검증·데이터셋 저장도 구현했다([결과](31-dataset-storage.md)). 32일차 품질 검사·보고서도 구현했다([결과](32-data-quality.md)). 33일차 이상은 미구현·계획이다. 아래 과거 설명보다 [최신 30~78일차 순서](30-roadmap-reordered.md)를 우선한다.

| 33 | P1 | B+D | 데이터셋·기간·상태·담당 필터(R08) | 요약과 목록에 동일 조건 적용 |
| 34 | P1 | C+D | 업무 상태 변경 이력(R09) | 실제 변경 시각 보존, 과거 추정 금지 |
| 35 | P1 | B+D | 정확한 기간 추이·CSV 내보내기(R09) | 이력 기반 차트·CSV 결과 일치 |

**변경된 우선순위:** 이미 완료된 1~32일차 다음에는 33~68일차 내부 기능과 안전장치를 개발하고, 69~73일차 외부 API 연동, 74~78일차 종합 테스트를 진행한다. 70일차가 공공데이터 API, 77일차가 학교 LAN 4대 AC15 검증이다. 각 기능의 단위·안전 확인은 개발 중 수시 진행한다. 수업 제출 마감이 개발 순번보다 앞서면 필수 과제 검증을 우선해 별도 수행한다.

### 4. 회원 등록 및 로그인 설계안

- 기존 인증은 `guests` + 초대 코드 + `guest_sessions` 방식으로 유지합니다. **26일차에 정식 아이디·비밀번호 인증을 별도 회원 세션으로 추가**했으며 기존 작업실 권한과의 연결은 27일차 예정입니다.
- 신규 회원: `users`(회원 ID, 로그인 ID 또는 이메일 UNIQUE, 표시 이름, `password_hash`, 생성일 등), 회원 세션 관련 테이블과 연관 모델을 추가. `password_hash()`/`password_verify()` 사용. 비밀번호 평문과 인증 토큰 원문은 DB·Git에 저장하지 않음.
- 기존 데이터 유지: 계정과 게스트 연결 규칙(예: `guest_user_links`)을 마련하고 계정 소유가 검증된 경우에만 연결. 초대 코드·표시 이름만으로 다른 계정의 기존 세션이나 프로젝트 소유권을 넘기지 않음.
- 새 화면: 회원가입·로그인·로그아웃·로그인 상태 표시, 기존 게스트 입장 선택지(유지 범위 별도 결정). 관리자·편집자·열람자 권한은 서버에서 매번 검증.
- 26일차 구현 API: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`. 기존 `/api/me`는 게스트 정보로 유지합니다. 작업실·Socket.IO 티켓의 회원 연계는 27일차 범위입니다.
- 보호: 입력 검증·로그인 시도 제한·쿠키 HttpOnly/SameSite, CSRF 보호, 세션 재발급/폐기. 외부 공개 서비스라면 HTTPS 필수.

### 5. 통계 대시보드·시각화 설계안

| 구성 요소 | 표시 형태 | DB 기반 집계·표현 기준 |
|---|---|---|
| 업무 상태 분포 | **파이차트 또는 도넛 차트** | `tasks.status` 별 건수와 비율. 전체 0건이면 안내 표시 |
| 담당자별 업무량 | **막대 차트** | 프로젝트 멤버별 담당 업무 건수·완료 건수 |
| 일/주별 생성·완료 추이 | **선 그래프** | 업무 생성 시각과 상태 변경 이력. 이력 도입 전 과거 완료일 추정 금지 |
| 핵심 지표 | **숫자 카드(KPI)** | 전체 업무, 완료율, 미완료 기한 초과, 체크리스트 완료율 |
| 데이터 상세 | **정렬·검색 가능한 표** | 업무 ID·제목·상태·담당·마감·출처 등 |
| 공공데이터 시각화 | **파이·막대·선·표 중 선택** | 원본 데이터의 범주/날짜/숫자 필드 매핑 결과만 사용 |

- 프론트엔드: 기존 순수 HTML/CSS/JavaScript에 **Chart.js(로컬 설치본)** 도입 제안. 반응형 레이아웃, 툴팁, 범례, 필터, 로딩·오류·빈 결과 UI 포함.
- 백엔드: `GET /api/projects/{id}/analytics/summary`, `.../status`, `.../assignees`, `.../trend` 등 집계 API 후보. 기간·상태·담당자 필터를 서버 SQL에도 적용.
- 범위: 프로젝트별 접근 권한 검사, 업무 삭제·상태 변경 시 재집계. 실시간 Socket.IO 이벤트 또는 짧은 주기 갱신으로 화면 동기화.
- 시연 데이터는 **예시 데이터**로 표시. 실제 통계와 분리하고, 0으로 나누기·마감일 없는 업무 등 예외 처리.

### 6. 공공데이터 및 파일의 간편 불러오기 설계안

**사용자 흐름:** 작업실 → `데이터 관리` → `데이터 가져오기` → (① 파일 또는 ② 공공데이터 API) → 미리보기 → 열/필드 매핑 → 유효성 검사 → 불러오기 실행 → 저장 데이터셋 선택 → 대시보드 차트 표시.

| 입력 방식 | 필수 UX | 백엔드 처리 |
|---|---|---|
| **CSV 업로드** | 파일 선택, 헤더·인코딩 감지(UTF-8 BOM 및 지원 가능한 국내 인코딩), 첫 20행 미리보기 | 크기·형식·행 수 제한, 날짜/숫자 값 검증, 잘못된 행과 사유 표시 |
| **JSON 업로드** | 파일 선택, 배열/객체 구조 확인, 선택된 데이터 경로 미리보기 | 허용된 JSON 형태 검증, 중첩 필드 펼치기·컬럼 매핑 |
| **공공데이터포털 API** | 미리 등록된 데이터 소스 선택, 조회 조건·기간·가져오기 버튼, 최종 갱신 시각 | PHP 서버에서 공식 API 호출, JSON/XML 파싱, 페이지 단위 적재, 중복 식별·실패 재시도·캐시 |
| **저장된 데이터셋** | 목록·검색, 미리보기, 새로고침, 삭제, 시각화 연결 | DB에서 데이터셋·행·가져오기 이력 관리, 프로젝트 권한 확인 |

- 데이터 저장 제안: `import_datasets`(출처·스키마·갱신 시각), `import_rows`(데이터 행), `import_runs`(수집 시간·성공/실패·행 수). 기존 `tasks`와 혼합하지 않고 출처를 유지. 사용자 명시 승인 없이 외부 행을 업무로 자동 등록하지 않음.
- **컬럼 매핑:** 범주형(파이/막대), 날짜형(선), 수치형(합계/평균/건수) 매핑. 미리보기 단계에서 축·집계 방식 지정. 중복 행은 키 기준 건너뛰기/업데이트 중 선택.
- **공공 API 사용:** [공공데이터포털](https://www.data.go.kr/)에서 실제 제공 중인 **특정 서비스 하나를 먼저 선정**하고 해당 서비스 문서의 승인·데이터 포맷·호출량·이용허락 조건을 확인. 무작위 URL 요청 대신 사전에 등록한 공인 API 주소만 호출하여 SSRF 차단. 서비스키는 서버의 `.env`에만 두고 브라우저·Git에 노출하지 않음.
- 장애 대비: 학교 LAN에서 공공 API가 막혀도 이전에 DB에 정상 적재한 **마지막 수집 데이터**를 보여 주고, 파일 가져오기 방식으로 시연 가능하도록 구성. 실패를 성공으로 표시하지 않음.
- 사용자 편의: 불러오기 이력/상태/건수/오류 사유 표시, 데이터셋 재선택·삭제, 중복 방지, 로딩 및 빈 데이터 안내.
- 외부 데이터에는 **제공기관·원본 링크·조회 조건·수집 시각·라이선스**를 함께 기록. 개인 정보나 재배포 제한 데이터는 사전 검토.

### 7. 완료 확인 및 시연 시나리오

1. 새 회원을 가입시키고 `users` 테이블에 등록됐는지 확인; 잘못된 비밀번호는 거부되는지 검사.
2. 로그인 후 작업실에서 기존 업무를 만들고 상태를 바꾸면 대시보드 파이차트·KPI가 실제 DB 값과 함께 바뀌는지 확인.
3. 담당자별 막대 차트·기간별 선 그래프·원본 데이터 표를 비교해 숫자가 일치하는지 검사.
4. CSV 또는 JSON 표본을 업로드하고 **미리보기 → 컬럼 매핑 → 오류 검증 → DB 저장 → 차트** 순서로 확인.
5. 공식 공공데이터 API에서 데이터를 가져온 뒤 출처·갱신 시각을 표시하고 파이/막대/선 중 알맞은 시각화로 출력.
6. 외부 API 연결이 실패해도 이전 DB 데이터·오류 안내가 유지되는지, 다른 사용자가 데이터셋에 무단 접근할 수 없는지 확인.
7. 로그아웃하면 회원 세션이 무효화되고 재로그인 시 자신의 데이터가 복원되는지 확인.
8. 기존 실시간 화이트보드 수용 테스트(AC01~AC32) 재실행, 학교 PC 4대 검증(AC15) 별도 수행.

**과제 평가 대응:** (1) DB 기반 회원가입·로그인, (2) DB에서 읽은 통계, (3) 파이차트 등 복수 그래프와 표, (4) 자체 디자인, (5) 공공데이터/파일 가져오기 과정 및 출처를 발표에서 각각 보여 줍니다. AI를 통한 해석은 선택이며 통계 원천·공식 계산을 대체하지 않습니다.

### 8. 개발 시 주의 사항

- 기존 `README.md`의 구현 완료 표기나 테스트 합격 숫자는 신규 기능 구현 전까지 변경하지 않음.
- 실환경 운영 데이터의 삭제·마이그레이션 전에는 DB 백업 및 별도 테스트 DB에서 재현 필수. 기존 초기화 스크립트(`reset-demo.bat`)는 모든 프로젝트·이미지를 삭제할 수 있으므로 무심코 실행 금지.
- 과제의 원래 3주 범위 문서·구현 이력은 **당시 기록**으로 보존. 신규 25일차 이후 개발은 확장 과제 범위.
- 26일차 회원 인증, 27일차 회원 권한·실시간 세션, 28일차 통계 API, 29일차 차트까지 구현 기록이 있다. 30일차 CSV·JSON 업로드·미리보기를 추가 구현했다. 확정 데이터셋 저장(31일차)도 구현했으며 공공데이터 API(70일차)는 미구현·계획이다.

| 47~48 | E04 | 화이트보드 버전 기록·복원 | 과거 스냅샷, 복원 전 백업 |
| 49~50 | E14 | 조건 자동화 | 멱등성·순환·권한 제어 |

| 52 | E15 | 중앙선 크기 조절 | 드래그·키보드·캔버스 좌표 보정 |
### 3. 추가 기능 간 선행 관계와 개발 우선순위

- **우선 3종:** E01 차트 드릴다운, E10 데이터 품질 검사, E09 대시보드 저장 뷰. 이미 개발하는 SQL·차트·데이터 가져오기를 재사용하므로 효율적입니다.
- **협업 2차:** E11 회원 멤버 관리, E02 검색, E06 개인 홈, E05 템플릿, E13 전체 활동 기록, E03 알림, E07 의존 관계, E08 반복 업무, E12 접근성.
- **고난도 3차:** E04 보드 버전 복원과 E14 조건 자동화. 잘못 구현하면 데이터 손상이나 무한 반복을 발생시킬 수 있어 별도 안전성 검증 후 진행합니다.
- **기존 R09와 E13 구별:** R09는 정확한 업무 상태 추이 생성용 기록, E13은 생성/담당/마감/삭제를 포함한 일반 활동 이력입니다.
- **기존 실행 취소와 E04 구별:** 기존 Undo/Redo는 클라이언트 작업 흐름이고 E04는 DB에 저장된 과거 보드 버전을 독립적으로 복구하는 기능입니다.

## 27일차 상태 갱신

회원 작업실 초대·전환, 본인 비밀번호로 기존 게스트 연결, 회원 세션에 종속된 HTTP·Socket.IO 접근 검사를 구현했습니다. 현재 29일차까지 구현 기록이 있으며 학교 PC 4대 AC15는 77일차 최종 검증에 배치했습니다. 상세 결과는 [27일차 문서](27-member-access.md)를 참고합니다.

## 28일차 상태 갱신

업무 원본을 기준으로 상태·담당자·마감·체크리스트 통계 API를 구현했습니다. 기간은 업무 생성일 기준이며 상태·담당자 조건과 함께 모든 지표에 적용합니다. 차트 UI는 29일차에 구현됐고 과거 완료 추이는 35일차 개발 계획입니다. [28일차 계약](28-task-analytics.md).

## 2026-10-20 개발 일정 재배치 확정

기준은 [30~78일차 최신 순서](30-roadmap-reordered.md)이며, **내부 기능 30~63일차 → 안전장치 64~68일차 → 외부 API·연동 69~73일차 → 종합 테스트 74~78일차** 순으로 진행한다. 이전 단락의 ‘31일차 공공 API’, ‘34일차 최종 테스트’, ‘52일차 확장 통합 테스트’ 등 기존 기획 순서와 상충하면 이 새 순서를 우선한다. 1~29일차 과거 구현 기록과 당시 테스트 결과는 변경하지 않는다.
